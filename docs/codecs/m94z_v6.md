# TTI-O M94.Z — V6 Segmented Adaptive Qualities

> **Status:** shipped (CPU implementation) in all three SDKs, with a
> cross-SDK golden fixture pinning the output bytes. Defaults fixed by
> the ratio sweep in section 6. V6 is never chosen by auto-tune; it is
> reached only through strategy hint 8 (`HINT_V6` / `TTIOM94ZHintV6`,
> or `TTIO_M94Z_HINT` set before block 0), or by writer policy. V5
> remains the default.

V4 and V5 code a block's qualities as one adaptive range-coder chain.
The model and the coder state carry across the whole block, so a 64 MiB
block cannot be split across compute units, and the qualities codec is
about 73% of encode CPU. V6 splits the block into N independent chains
so the work can be spread across cores.

Splitting costs ratio: each chain starts from a cold model, so a block
pays N model warm-ups instead of one. Two measures hold that cost down
without giving up segment independence: the cold prior is sized to the
block's real quality alphabet, and it is seeded from the block's
symbol histogram, and the context space is kept small enough that each
context still sees enough symbols to learn. What remains is 3.8 to 5.9%
against V4 at the default segment size; section 6 records it per corpus
and explains why the comparator is V4 rather than whatever the umbrella
picks today, and section 9 covers the optional sequence-context field.

---

## 1. Outer container

Unchanged from V4 and V5: the M94Z container written by
`m94z_pack_any`, with version byte `6` and the body-kind flag `0x02`.

| Offset | Size | Field |
| --- | --- | --- |
| 0 | 4 | magic `M94Z` |
| 4 | 1 | version = 6 |
| 5 | 1 | flags; bit 1 set, bits 4-5 pad_count |
| 6 | 8 | num_qualities (LE u64) |
| 14 | 8 | num_reads (LE u64) |
| 22 | 4 | rlt_len (LE u32) |
| 26 | rlt_len | read-length table, zlib |
| 26+rlt_len | 4 | body_len (LE u32) |
| 30+rlt_len | body_len | V6 body, section 2 |

Decoders dispatch on the version byte exactly as they do today. A
decoder that does not know version 6 rejects the stream at the same
point it rejects any other unknown version.

## 2. Body layout

All integers little-endian.

| Offset | Size | Field |
| --- | --- | --- |
| 0 | 1 | body_version = 1 |
| 1 | 1 | reserved = 0 |
| 2 | 2 | segment_count N (u16, >= 1) |
| 4 | 4 | segment_symbols S (u32) |
| 8 | 1 | qbits Q |
| 9 | 1 | qshift |
| 10 | 1 | pbits P |
| 11 | 1 | pshift |
| 12 | 1 | dbits D |
| 13 | 1 | sbits S (0 = no sequence context, section 9) |
| 14 | 2 | alphabet_size A (u16, 1..256) |
| 16 | A | alphabet[A] (distinct quality bytes, ascending) |
| 16+A | 2A | seed[A] (u16, seed frequency per dense symbol, all >= 1) |
| 16+3A | 4N | seg_len[N] (u32, compressed length of each chain) |
| 16+3A+4N | ... | N chain bodies, back to back |

Bytes 8 to 15 are the `model_config[8]` field named in the design
document.

`alphabet[]` lists every quality byte the block uses, ascending, and
symbols are coded as indices into it. Segments restart their models
constantly, so the cold prior must not spread mass over values the
block never emits: with binned Illumina qualities the real alphabet is
a handful of values, and a 256-symbol prior costs several bits per
symbol that a short segment never earns back. V4 gets the same effect
from the `max_sym` its stats pass records. The indices are also what
the context word uses, which keeps `qctx` and the delta bucket tight.
A decoder rejects a stream whose alphabet is not strictly ascending.

`seg_len[]` makes every chain independently addressable. A decoder
computes each chain's offset by summing the preceding lengths, so
chains can be decoded in any order, in parallel, or selectively: a
reader that wants one slice of a block decodes only the segments
covering it.

## 3. Segmentation

Segments hold whole reads. Starting from the first unassigned read, a
segment accumulates reads until its symbol count reaches S, and closes
at that read boundary; the final segment holds whatever remains and is
usually short. A read is therefore never split across segments, and a
segment never begins mid-read.

The rule is deterministic and depends only on the read-length table, so
an encoder and a decoder derive the same segmentation independently.
The segmentation is not stored beyond N and S.

Consequences worth stating plainly:

- A single read longer than S becomes a segment of one read. S is a
  target, not a bound.
- N follows from the read lengths and S; it is recorded so a decoder
  need not recompute it before reading `seg_len[]`.
- Because segments are contiguous rather than striped, each model sees
  a locally homogeneous run of qualities. Striping would spread each
  model across the whole block and cost more ratio, not less.

## 4. Context model

Each segment is coded independently: a fresh model array and a fresh
`rc_cram` coder, with no reference to any other segment. The range
coder is the existing CRAM one, unchanged.

The model is `native/src/v6_model.h`, which keeps symbols in dense
alphabet order and their cumulative frequencies in a Fenwick tree, so a
lookup is O(log nsym) with a fixed step count. V4 and V5 keep using
`sm_model`, which searches by walking the frequency array from the
front; those are shipped formats and must keep producing the bytes they
produce today. The change is ratio-neutral by construction, because the
range coder advances as `range = (range / tot) * freq`, which does not
involve the cumulative frequency: the sequence of interval widths, and
therefore the output length, is identical either way. Measured on all
four corpora, the compressed totals are byte-for-byte the same.

The context word is built from three fields, plus the optional
sequence field of section 9, totalling C = Q + P + D + S bits:

    ctx = (qctx & ((1 << Q) - 1))
        | (pos_bucket   << Q)
        | (delta_bucket << (Q + P))
        | (seq_ctx      << (Q + P + D))

- `qctx` is the running quality context, updated per symbol as
  `qctx = (qctx << qshift) + q`, and **reset to 0 at the start of each
  read**.
- `pos_bucket = min((1 << P) - 1, (len - 1 - i) >> pshift)`, where `i`
  is the symbol's index within its read and `len` the read length. It
  buckets distance from the end of the read, which is where quality
  degrades.
- `delta_bucket = min((1 << D) - 1, |q_prev - q_prev2|)` for `i >= 2`,
  and 0 for the first two symbols of a read. `q_prev` and `q_prev2`
  reset with each read.

Constraints: `Q + P + D + S <= 16` and `qshift <= 8`. A parameter set
violating either is rejected at encode.

Model memory follows from the context count and the alphabet. Each
context holds `freq[A]` plus a Fenwick tree of `A + 1` entries, all
u16, so a segment costs

    2^C * (2A + 2) * 2 bytes

The design document quotes `2^C * n_symbols * 2` against a 256-symbol
alphabet, which is 2 MiB per segment at C = 12. The dense alphabet and
the smaller context space together make the real figure far smaller: at
C = 12 on the lowcov corpus it measures 0.80 MB per segment. Context
bits still trade against how many segments can be resident at once,
which is why section 6.1 settles them against throughput as well as
ratio.

Because every segment needs a cold model, the per-context allocation
the V5 body performs once per block would happen N times per block
here. The implementation allocates the whole model array for a segment
as one contiguous block instead.

### 4.1 Seeding

Every context in every segment starts from `seed[]` rather than from a
uniform prior, so a segment opens at the block's marginal distribution
instead of learning it again. `seed[i]` is the block histogram scaled
to a total of about 256 and clamped so every present symbol keeps at
least 1; the scaling is integer, so both directions build the identical
table. Symbols stay in dense alphabet order: the Fenwick tree makes the
search independent of where a symbol sits, so there is nothing to gain
from ordering by frequency and it would only add a way for the two
directions to disagree.

The seed mass is deliberately small. It is flat between 256 and 384,
and at 4096 or above the result is worse than not seeding at all: a
heavy prior is slow to be overridden by `SM_STEP` increments, and the
block marginal is a poor fit for any individual context. The mass is an
encoder choice and is not recorded in the wire; only the resulting
weights are.

## 5. Determinism

The encoded bytes must not depend on how the work was scheduled. Three
properties hold:

- **Thread count.** Segments are encoded independently and concatenated
  in segment order, so output is identical for any thread count.
- **Run to run.** Nothing in the coder consumes time, addresses, or
  entropy from the environment.
- **Implementation.** Python, Java and Objective-C all reach the same
  kernel, and the cross-SDK golden fixture pins the bytes.

A later GPU implementation is held to the same contract: it must
produce the identical byte stream, not merely a stream that decodes to
the same qualities.

## 6. Measured ratios

Measured with `native/bench/bench_v6_ratio.c` over 256 MB samples per
class (lowcov is 178 MB, the whole corpus), split into read-aligned
64 MiB blocks, which is the block size a real encode uses.

V6 is compared against **V4**, not against the strategy the umbrella
picks today. V6 has no sequence field, and on lowcov the umbrella picks
V5, which wins there precisely by using the sequence channel: V4 alone
is itself +24.02% on that corpus. Comparing V6 to V5 would be scoring
it against a channel it was specified not to have. V5 remains the CPU
fallback, so nothing shipped regresses; V6 trades ratio for the ability
to spread one block across many compute units.

Defaults, fixed here: Q 6, qshift 7, P 4, pshift 4, D 1, seed mass 256,
S = 1 Mi. Section 6.2 has the sweep that sets S.

| Corpus class | V4 | V6 at S = 1 Mi | vs V4 | at S = 256 Ki |
| --- | --- | --- | --- | --- |
| HiFi | 3.1983 b/q | 3.3718 b/q | +5.42% | +6.25% |
| NovaSeq WGS | 1.1628 b/q | 1.2312 b/q | +5.89% | +6.18% |
| 2x250 chr22 | 2.0899 b/q | 2.1799 b/q | +4.31% | +6.66% |
| lowcov chr22 | 2.9444 b/q | 3.0548 b/q | +3.75% | +5.99% |

The HiFi row is `hg002_hifi_subset` as its `plan.json` defines it,
264 190 341 bases, which is a different sample from the one the earlier
HiFi row was taken over; the other three reproduce that row's V4
baseline to four figures.

On lowcov the same stream is +28.67% against the V5 baseline the
umbrella would otherwise pick, and +31.45% at the earlier S = 256 Ki.
Segment size does not close that gap: it settles near +27% by S = 8 Mi,
which is still worse than V4's own +24.02% there. The gap is the
sequence channel, not segmentation.

### 6.1 Context bits are far below V4's

C = Q + P + D = 11 here, where V4 uses up to 16. That is not a
concession, it is the better setting: V4 models a whole 64 MiB block
and can afford a large context space, but a V6 segment is a few hundred
thousand symbols, so a 2^14 context space leaves each context too
sparse to learn and the model spends the segment warming up instead of
predicting.

Sweeping every split of C from 6 to 15 over all four corpora and taking,
for each C, the split whose worst corpus is best:

| C | Best split | Worst corpus | HiFi | NovaSeq | 2x250 | lowcov |
| --- | --- | --- | --- | --- | --- | --- |
| 8 | Q5 P3 D0 | +9.04% | +5.31% | +8.76% | +6.04% | +9.04% |
| 9 | Q5 P3 D1 | +7.44% | +5.71% | +6.79% | +6.09% | +7.44% |
| 10 | Q6 P3 D1 | +6.79% | +6.06% | +6.79% | +6.09% | +5.99% |
| 11 | Q6 P4 D1 | +6.66% | +6.12% | +6.18% | +6.66% | +5.99% |
| 12 | Q6 P5 D1 | +6.66% | +6.24% | +6.18% | +6.66% | +5.99% |
| 13 | Q7 P5 D1 | +6.66% | +6.41% | +6.18% | +6.66% | +5.99% |
| 14 | Q7 P5 D2 | +7.27% | +6.84% | +5.98% | +7.27% | +6.96% |

C = 11 is the smallest split reaching the best worst case, so it is the
default. Above it the ratio stops improving and the model keeps growing;
below it NovaSeq starts to suffer.

The delta field is worth stating separately: **D = 1 is the setting, not
0 or 2.** One delta bit is what NovaSeq needs, and dropping it costs
NovaSeq about 0.8 points while a second bit costs the other three
corpora more than it returns. Both the original plan's grid (which
specified Q in 8..12) and the first retune missed this, the plan because
it never went below Q = 8 and the retune because it varied Q and D
together.

The choice also runs with the GPU rather than against it. Model memory
is `2^C * (2A + 2) * 2`, so every context bit doubles the per-chain
working set, and the Phase 2 spike measures GPU encode tracking that
almost inversely: on lowcov at 1024 chains, 131.6 MB/s at C = 14 against
225.7 MB/s at C = 11. C = 10 buys a further 2% of throughput for 0.6
points of ratio on NovaSeq, which is not a trade worth taking.

### 6.2 Where the rest of the cost goes

Segment size is the remaining term. It was first sized against how many
chains a GPU could run at once; that backend is gone, and the sweep
below is at the shipped C = 11 rather than the earlier C = 14, so it is
what sets S now. Against V4, with encode throughput on 16 cores:

| S | HiFi | NovaSeq | 2x250 | lowcov | HiFi MB/s |
| --- | --- | --- | --- | --- | --- |
| 256 Ki | +6.25% | +6.18% | +6.66% | +5.99% | ~510 |
| 512 Ki | +5.84% | +5.99% | +5.27% | +4.67% | ~550 |
| **1 Mi** | **+5.42%** | **+5.89%** | **+4.31%** | **+3.75%** | **~530** |
| 2 Mi | +5.13% | +5.83% | +3.66% | +3.14% | ~521 |
| 4 Mi | +4.97% | +5.80% | +3.24% | +2.76% | ~505 |
| 8 Mi | +4.87% | +5.78% | +2.96% | +2.53% | ~408 |

S = 1 Mi is better than 256 Ki on ratio for all four classes and on
encode throughput as well, and leaves 64 segments in a 64 MiB block,
more than a 16-core machine can use. Past 2 Mi the ratio flattens while
the throughput falls away, and at 8 Mi a fifth of it is gone for a
quarter of a point. The older table below was measured at C = 14 and is
kept because it is the only run that includes the segmentation floor:

| S | HiFi | NovaSeq | 2x250 | lowcov |
| --- | --- | --- | --- | --- |
| 128 Ki | +9.86% | +6.26% | +12.77% | +12.64% |
| 256 Ki | +8.81% | +5.77% | +9.91% | +10.35% |
| 512 Ki | +7.46% | +5.46% | +7.45% | +8.16% |
| 4 Mi | +4.91% | +5.00% | +2.88% | +3.18% |
| one segment | +3.56% | +4.82% | +0.34% | +0.34% |

"One segment" means one segment per 64 MiB block, which is V6 with
segmentation switched off. It is the floor, not a shippable
configuration. Two classes reach it almost exactly, which says the
context word is sound; NovaSeq's +4.82% floor is the model itself being
simpler than V4's, which carries a quality map, per-position selectors
and duplicate handling.

Three implementation choices carry the ratio that V6 does achieve:

- **Dense alphabet** (section 2). Sizing the cold prior to the block's
  real alphabet instead of 256 symbols is worth about 6 points on
  lowcov, and shrinks the model by roughly 5x as a side effect.
- **Histogram seeding** (section 4.1). Priming every segment from the
  block's marginal distribution is worth a further 0.6 to 3.3 points.
- **A small context space** (section 6.1), worth 1 to 2.5 points more.

## 7. Engines and the TTIO_GPU knob

V6 blocks encode on the CPU unless a GPU engine is asked for by name:

| Variable | Effect |
| --- | --- |
| `TTIO_GPU` | `off` (default) or `force`. Anything else reads as off. |
| `TTIO_GPU_DEVICE` | Physical device index. Default: first discrete device that supports 8- and 16-bit storage. |
| `TTIO_GPU_SLOTS` | Concurrent block slots, at most 8. Default: derived from device-local memory. Measured gains stop after two on the development GPU. |
| `TTIO_GPU_MAX_CHAINS_PER_DISPATCH` | Upper bound on chains per dispatch, so no single dispatch trips a display driver's timeout watchdog. |

Selection is explicit because a GPU being present is not evidence that
using it helps. On the development laptop a real discrete GPU is
present and using it is slower than the CPU path on three of four
corpora, so a presence-based rule would make things worse.

**Enabling the engine is a storage decision, not only a speed one.** The
writer then emits V6, which is 6 to 7% larger than V4, and that cost
belongs to the file for as long as it exists. A reader on another
machine cannot fall back on bytes already written. Encode speed is a
per-machine choice; output size is not.

If the engine is asked for and cannot come up, the run logs one line,
encodes on the CPU, and does not emit V6: writing V6 without an engine
would give larger files and no speed at all.

Both engines produce identical bytes, which is what makes it safe for a
single file to contain blocks from both. That is enforced by a CI gate
comparing GPU output against the CPU coder, not assumed.

## 8. Strategy integration

- `TTIO_M94Z_HINT_V6` is 8, the next value after `TTIO_M94Z_HINT_V4_AUTO`.
- `ttio_m94z_qual_stream_strategy` returns 8 for a version-6 stream.
- Auto-tune never selects V6. V6 does not beat V4 or V5 on size, so it
  must not enter a size race it would only win by accident. It is
  selected by explicit hint, or by writer policy.
- Decoding a V6 stream requires no sequences provider when the body
  header's `sbits` is 0, which it is in every stream written before
  that field existed and in every stream the writer produces today. The
  context word is then built from qualities, positions and deltas only.
  A stream carrying `sbits` > 0 cannot be decoded without the sequences
  channel; see section 9.

## 9. The sequence-context field

Body header byte 13 carries `sbits`, the width of a V5-style sequence
context spliced onto the top of the context word:

    [ qctx : qbits ][ pos : pbits ][ delta : dbits ][ sctx : sbits ]

`sctx = ((sctx << 2) | bcode) & ((1 << sbits) - 1)`, rolled BEFORE
coding `q_i` so the window includes the base at this position, reset
per read, with `bcode` A/a 0, C/c 1, G/g 2, T/t 3 and anything else 0.
That is V5's field, unchanged. An odd `sbits` masks a partial base, as
V5's own S5 does at 5 bits.

The byte is 0 in every stream written before the field existed, and 0
is exactly "no sequence context", so old streams decode unchanged and
still need no sequences provider. `C = qbits + pbits + dbits + sbits`
is still capped at 16, so every bit given to the window is taken from
somewhere else.

Measured at S = 1 Mi, Q6 qshift7 P4 pshift4 D1, against the strategy
the umbrella pins:

| Corpus class | pinned | sbits 0 | sbits 2 | sbits 4 |
| --- | --- | --- | --- | --- |
| HiFi | V4 | +5.42% | +6.73% | **+3.76%** |
| NovaSeq WGS | V4 | +5.89% | **+5.15%** | +5.38% |
| 2x250 chr22 | V4 | **+4.31%** | +6.88% | +11.52% |
| lowcov chr22 | V5 | +28.67% | +21.90% | **+14.46%** |

The field is worth most exactly where V6 was weakest: on lowcov, the
one class where the umbrella pins V5, it halves the gap, and V6 goes
from far behind V4 to well ahead of it. On HiFi it is worth a point and
a half. On NovaSeq it is close to neutral.

On 2x250 it is a loss, and a large one. The context space grows
sixteenfold at sbits 4 and the per-segment warm-up that costs is more
than that corpus gets back from knowing the base. No single width is
right for all four, so `sbits` is a per-run choice of the same kind the
qualities strategy already makes, and not a fixed default.

The wider context also costs encode throughput, 15 to 25 per cent at
sbits 4, because the per-context model no longer fits where it did.
